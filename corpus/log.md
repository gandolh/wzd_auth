## [2026-09-01] decide | Round 4 settled; the design grilling is complete at 13 decisions. A grant carries a **set** of roles, not one — rejected single-role (simpler, matches prm today) because a set costs nothing now and avoids a migration the first time any of six apps needs two at once. Registration is open **per app via a flag, closed by default** — rejected Ward-level signup because it fails in the wrong direction, leaving a new app reachable by strangers until someone remembers to close it; the flag fails safe. Lifetimes: 15-minute access token, 30-second introspection cache, 30-day rotating refresh — recorded that the 30 seconds is the number that matters, since apps introspect on every request, and that logout is near-instant in practice because it clears the cookie, leaving the window exposed only to an already-stolen token. ## [2026-09-02] build | Wave 2 landed — briefs 01 (schema) and 02 (signing keys). Six tables in one baseline migration with a thin query module each, plus Ed25519 signing, a published JWKS and 15-minute access tokens. The test runner landed here too, ahead of both briefs, because both had tests in their acceptance criteria and brief 00 had wired a `test` script with no runner behind it; 125 tests now, vitest at the repo root with `pool: "forks"` because better-sqlite3 is a native addon. **Both implementing agents were killed mid-run by a quota limit after finishing the work but before reporting**, so their handoff contracts were reconstructed from source by the controller and are recorded in the two outcome notes — verified against code, not an author's summary. Two review passes found seven issues, each reproduced by execution before the fix and re-run after. The two that mattered: (1) `verifyWardAccessToken` spread a caller-supplied options bag **after** the pinned issuer, so any call site could set `clockToleranceSeconds` (an unbounded lifetime extension), `issuer: undefined`, `audience`, or `currentDate` — all four confirmed accepting a token expired 30 days ago or one minted by `https://evil.example`. It now takes a token and nothing else; a spread reorder was rejected as a fix because it still type-checks the dangerous fields and the next refactor reopens the hole, and brief 08 re-exports this surface into six apps. (2) `grantTargetId` joined components with `:` while role strings are explicitly opaque and unrestricted — the tests deliberately grant one containing `:` — so `("atrium", "a:b")` and `("atrium:a", "b")` produced an identical `target_id`, silently breaking the console's "everything that happened to this grant" filter, which is the one job audit_log exists to do. Components are percent-encoded now, with a `parseGrantTargetId` to decode; **the encoding changed rather than the allowed role charset**, since role opacity is locked in decisions-accounts.md. Also fixed: `keygen --force` could not restore 0600 and printed 0600 regardless (writeFile's `mode` applies only on create, so a forced overwrite inherited whatever a restore had left); the loader booted silently on a world-readable key, and now warns rather than refuses, because refusing on a permission bit turns hardening into an outage mid-recovery; the previous-key slot was additive trust granted by a filename — an unrelated Ed25519 key dropped at `<key>.previous.pem` minted a token for an arbitrary subject that verified cleanly, the asymmetry being that filling that slot needs only **write** access where abusing the current key needs **read** — now logged at warn with the rotation lifecycle documented; `jwksUrl`'s base path defaulted to `""`, resolving to `https://origin/.well-known/jwks.json` while Caddy serves Ward under `/ward-api/*`, so the documented usage would have made all six apps fetch a 404 and reject every token (fails closed, so an outage rather than a bypass, but a wrong default in the one module brief 08 lifts unchanged — it is required now, so a wrong value is a compile error at the call site); and `grants.granted_by` was nullable while its own comment promised it answers "who granted this" even if the log is pruned. **Recorded as a standing constraint:** the baseline migration was edited in place during that fix round, which was safe only because no persistent database existed yet — every applied copy was a scratch database in a test. It freezes when brief 11 deploys, after which a schema change is a new migration appended to `MIGRATIONS`, never an edit, because the runner records the name and an edit to an applied migration is silently skipped on every existing database. Three properties were confirmed by review to hold **structurally** rather than by care, worth knowing before anyone simplifies them: private key material cannot reach the JWKS (the published JWK is built field-by-field from an allowlist and an unexpected parameter fails at boot, so a future key type refuses to start rather than leaking), the algorithm is genuinely pinned (`alg: none`, `HS256` signed with the public key's own bytes, `Ed25519`, and `constructor` — which would otherwise index the library's lookup table into `Object` — all rejected), and refresh rotation is atomic (`claimRefreshToken` and `revokeFamily` are each a single `UPDATE ... RETURNING`, which is what brief 03's reuse detection rests on). One sharp edge left unfixed and recorded instead, because no call site is wrong today: "current key signs" is conventional, not structural — `getKeySet()` exposes `.previous` and the low-level `signAccessToken` accepts any key, so briefs 03 and 04 should mint through `mintAccessToken(subject)` and nothing else.

## [2026-09-04] build | Wave 3 landed — briefs 03 (login, refresh rotation, lockout) and 06 (the superuser and its console session). Ward can now authenticate somebody: 315 tests, up from 270. Recorded three of brief 03's resolutions as decisions in wiki/decisions-implementation.md — the **absolute** 30-day refresh-family lifetime (a sliding expiry was rejected because it makes a family immortal for as long as anyone keeps rotating it, and the party most likely to rotate quietly forever is a thief; the reuse alarm only fires when the victim returns, and a victim who has stopped using the app never does), logout revoking rather than deleting (the `revoked_reason` column exists so the console can tell a logout from a rotation from a theft signal, and DELETE erases exactly what an operator investigating a stolen session needs), and the lockout key never being `request.ip` (Ward binds loopback behind Caddy, so `request.ip` is `127.0.0.1` for the entire internet and the sixth failed login anywhere would lock out everybody; the **last** `x-forwarded-for` element is used because Caddy appends the peer it observed, so a client prepending a spoofed value only adds an element nobody reads). **Two review passes found thirteen issues, and the two worst broke ordinary use rather than resisting an attack.** (1) Two tabs refreshing at once destroyed the session: the single-use UPDATE held — only one caller wins it — but the loser's reuse sweep revoked the winner's brand-new R2, leaving zero live tokens and a false theft record. On a one-origin estate where six apps share one access cookie at `Path=/`, several tabs waking together is the expected shape, and a StrictMode double-effect does it too. A used token presented again is now a **race** rather than a theft when its family still has a live successor issued within ten seconds. **That fix was itself incomplete and the reviewer caught it**: the controller first ruled the raced response must stay byte-identical, which left cookie-clearing headers on the loser's 401 — and since both responses race into one shared cookie jar, a loser landing second dropped the tokens and signed the person out anyway, turning a certain loss into a coin flip. The raced branch now clears nothing, on the reasoning that clearing exists to stop a client looping on a **dead** session, so in a race it does not tidy up after the session, it destroys it. What that concedes is a `Set-Cookie`-shaped signal that the token was genuine and freshly rotated, available only to someone already holding it who could learn the same by retrying after the window. (2) One valid account bought unlimited password guessing, because `clearFailures` was keyed on address: four wrong guesses at a victim then one correct login to the attacker's own account reset the counter — 40 guesses accepted with zero 429s, and prm ships public registration so brief 07 makes obtaining that account self-service. The lockout **decision** stays on the address; **forgiveness** is now per account, with the per-address breakdown capped because anonymous input feeds it. Also fixed: a cross-site form POST signed the victim out of the whole estate silently (SameSite=Lax stops cookies being *sent* cross-site, not a response *deleting* them, and `enctype="text/plain"` slips past Fastify's content-type rejection — cookies are now cleared only when a token was presented, and both routes refuse a request whose `Sec-Fetch-Site` or `Origin` says cross-site, while absent headers still pass because server-side clients send neither); the break-glass credential shared its lockout budget with ordinary login, so anyone could lock the operator out of the one credential that still works when `/login` is under attack; `consoleCookieSecure()` failed open where its sibling fails closed, shipping the console cookie without `Secure` on a plain-HTTP hostname; minting after the rotation commit burnt families on a dropped response; a loopback caller with no forwarded address silently collapsed the estate into one lockout bucket; an unauthenticated 500 echoed the signing key's absolute filesystem path to anyone on the internet; and the reuse alarm recorded no presenter address while being writable without bound by replaying one spent token. **The superuser's load-bearing property holds structurally, not by convention:** a console token is `wcs_` + random with **one** dot-separated segment where a compact JWS has three, so the access-token verify path rejects it as `JWSInvalid` — it cannot accidentally satisfy an app's ordinary auth check because it is not the same kind of thing. There is no `isSuperuser` branch anywhere in production code, and brief 04 needs none either; "console only" falls out of the superuser having no grants. Its session lives in an in-memory map with no table, so "the superuser has no row anywhere" is literally true. **One acceptance criterion is deliberately owed forward:** brief 06's most important test — a superuser console token presented to `/introspect` returns `active: false` — could not be written because `/introspect` is brief 04. It is asserted structurally in wave 3 and carried to brief 04 as a required test.

## [2026-09-04] build | Wave 4 landed — briefs 04 (introspection) and 05 (apps, grants, accounts, audit), plus the `sid` claim and the first integration tests. Ward is now a working identity service: it authenticates people, tells apps whether a session is live and what it may do, and administers the estate from a break-glass console. 444 tests, up from 315. **Brief 04's honesty is what made this wave matter.** Asked whether a revoked refresh family could be linked to a still-valid access token, it worked out that it could not — `jti` is a fresh UUID that is never persisted and no claim named the family — and said so instead of overclaiming. It implemented the strongest sound statement available (an account with no live refresh token has no live session) and **rejected a half-fix, recording why**: refusing tokens whose `iat` postdates the newest live refresh row catches about half the two-family orderings, rests on an invariant in a file it did not own, and fails by spuriously signing a legitimate person out of six apps. The controller then closed the gap properly with a **`sid` claim** carrying the refresh family id, so introspection asks whether *that family* is live. This was worth doing rather than accepting because of where the gap landed: decisions.md justifies the entire self-service UI on one feature — "sign out my other devices is the only self-serve response available to someone who suspects their session was stolen" — and that is exactly the case the gap broke, against an attacker who by hypothesis is actively using the token. Recorded in decisions-tokens.md, including why it does not contradict the no-permissions-in-claims rule: that rule exists because a token minted before a grant changed would carry **stale authority**, and a session id cannot go stale that way since it names a row whose liveness is read fresh every time. `sid` is identity, not authority, and is the standard OIDC name for it. Made **required** rather than optional in both the claim and the mint parameter, because an optional one lets a call site mint a silently unlinkable token and forces introspection to guess what an absent `sid` means — where the only safe answer is "not live", turning a forgotten argument into an outage instead of a compile error. `hasLiveFamily` also requires the family to **belong to the subject**; that pairing cannot be forged through `/introspect`, which reads `sub` and `sid` off one verified token, but the safety was living in the caller and brief 09's "sign out my other devices" is precisely the shape that pairs a subject from a session with a family id from a request. **The first integration tests landed and paid for themselves immediately.** Nine tests drive the real `buildApp()` against a real on-disk database and a real generated Ed25519 key over `app.inject`, closing the gap status.md had been naming as the biggest one — every prior test built its own Fastify instance or opened `:memory:`, so 429 tests overstated the confidence. They also settle two acceptance criteria neither brief could satisfy alone because each needed the other's endpoint, and flow 1 runs the estate's actual bring-up sequence, which nothing had ever executed. They found two behaviours no per-module test can reach: the **10-second refresh race carve-out swallows a replay that fires too soon** (a naive login → refresh → replay is treated as two tabs racing, so nothing is revoked — `refresh.ts`'s unit tests call `rotateRefreshToken` directly in whatever order they please and never hit it), and **`session.refresh_denied` is effectively unreachable** for the everyday disabled account, because `/refresh` peeks `sessionForRefreshToken` — which already excludes a disabled account — before the rotation that would write the row. Both are documented in code where they surfaced. Brief 06's owed acceptance test now lives in `introspect.test.ts`: a superuser console token returns `active: false`, and **nothing implements it**, which is the point — a console token has one dot-separated segment where a compact JWS has three, and the superuser holds no grants. Brief 04 also has no `isSuperuser` branch, as decisions-admin.md requires. Brief 05 proved the console surface closed with a real signed access token carrying two grants, refused through cookie, bearer and console-cookie alike. Two of its calls are worth knowing: a **no-op writes no audit row** (auditing double-clicks buries the rows an operator needs under noise they generated by mis-clicking, and every response carries a created/removed/changed flag so a UI can still tell), and **`app.registration` is a separate audit action from `app.update`**, because "who renamed this" and "who opened this to the public" are different questions. `decisions-implementation.md` hit the 200-line cap and was split by topic rather than by date: session mechanics settled during the build — the absolute family lifetime, logout revoking rather than deleting, and `sid` — moved to **decisions-tokens.md**, so a reader asking "how do sessions work" finds all of it on one page instead of having to know which half was decided when.
